The consolidator bounds the active observation buffer. When the pool of active observations grows large enough, the orchestrator selects the oldest overflow and hands it to a single background consolidator subprocess. That subprocess folds the observations into durable `.memory/<sessionId>/` topic files and updates JOURNEY.md, then exits. The orchestrator tombstones exactly the batch it handed over, draining the buffer back toward the pool target.

## Consolidator clock

The consolidator clock fires on the same two events as the observer clock: `turn_end` and `agent_start`. It evaluates these conditions in order:

1. `runtime.enabled` is true and `config.passive` is false
2. `runtime.consolidatorInFlight` is false — strictly one consolidator at a time
3. `poolTokens(activeObservations) >= config.consolidateAtPoolTokens` (default 15,000 tokens)

When all three hold, `selectPromotionOverflow(active, config.poolTargetTokens)` selects the oldest observations above `poolTargetTokens` (default 10,000 tokens). These are the ones that will be promoted.

## Oldest-first selection

The promotion batch is the observations that represent the oldest overflow above `poolTargetTokens`. Observations are sorted chronologically by their timestamp-id; the ones at the front — accounting for the most historical tokens — are selected first. The result is a `promote` array handed exclusively to this run.

The consolidator's kickoff prompt is built by `buildConsolidatorPrompt`: it includes the current local time, the current `INDEX.md` content, the current `JOURNEY.md` content, and the overflow observation lines formatted as `<timestamp-id>  <content>`.

## Subprocess spawn

The consolidator is spawned with the same `buildWorkerArgv` / `spawnWorker` pattern as observers:

```
pi --no-extensions --no-skills --no-prompt-templates --no-context-files --no-builtin-tools
   --model <provider>/<id> [--thinking <level>]
   -e agent/index.ts
   -n om-consolidator-<runId>
   -p "<prompt text>"
```

The environment variables set for the consolidator subprocess:

| Variable | Value |
|---|---|
| `OM_WORKER` | `"consolidator"` |
| `OM_RUN_ID` | The run id (e.g. `cons-20240115120000-12345-1`) |
| `OM_MEMORY_DIR` | Absolute `.memory/<sessionId>/` root — the consolidator's file sandbox |
| `OM_COST_PATH` | Absolute path to the cost handoff file |

There is **no result file** for the consolidator. Its output is the `.memory/` edits themselves. The orchestrator already knows the exact batch it handed over and tombstones it unconditionally on clean exit.

## Worker agent

The `agent/index.ts` extension for the `consolidator` role:

- `before_agent_start` replaces the system prompt with `CONSOLIDATOR_SYSTEM` — a detailed prompt covering topic routing, writing style, front-matter requirements, and JOURNEY.md maintenance rules
- `registerConsolidatorTools` registers five scoped file tools: `read`, `write`, `edit`, `ls`, `grep` — all confined to `OM_MEMORY_DIR` via `resolveWithinMemory`
- The run ends by **natural exit** — the model emits a one-sentence confirmation and the headless `pi -p` session terminates on its own; there is no terminal tool

All path arguments are resolved against the session memory root. Any path that escapes `.memory/` is rejected with an error response. `INDEX.md` is explicitly blocked from `write` and `edit` because it is regenerated by the orchestrator after every consolidator run.

## JOURNEY.md maintenance

The consolidator appends a short dated segment to `.memory/JOURNEY.md` on every run. The segment describes the arc of the batch it just processed — two to five sentences of past-tense, purely descriptive prose under a `## <date>` heading. Consolidator instructions explicitly prohibit recommendations, next steps, TODOs, or any forward-looking language.

When JOURNEY.md would grow past `journeyTargetTokens` (default 1,000 tokens), the consolidator compresses the **oldest** segments into a tighter summary at the top, leaving recent segments intact. This keeps the file bounded without discarding recent history. The current JOURNEY.md is included verbatim in the consolidator's kickoff prompt, so each run sees the full file and can update it in place with the `write` tool.

## Tombstoning

After the subprocess exits with code 0, the orchestrator:

1. Re-folds the **current branch** to get the live `activeObservations`
2. Intersects `promote.map(o => o.timestamp)` with `stillActive` — observations committed by an observer during the consolidator run are not in the handed batch and are therefore never accidentally tombstoned
3. Appends `om.observations.dropped` with `{ observationTimestamps: toDrop, coversUpToId: lastSourceEntryId(branch) }`
4. Re-renders `INDEX.md` from the updated topic files via `atomicWrite(indexPath(root), renderIndexFile(listTopics(root)))`

The handed batch is the enforcement mechanism. The consolidator must consolidate everything it was given — filing observations into topic files or discarding clear noise are both valid outcomes. It does not report back which observations it kept. On clean exit, the orchestrator trusts it and drops the whole intersected batch.

<Note>
The consolidator runs concurrently with in-flight observers. The compaction hook never waits for the consolidator (`consolidatorInFlight` is not tracked in `observerTasks`). A compaction that fires while a consolidation is running will render from the current active buffer, which may still include the observations being consolidated. Those observations will be tombstoned once the consolidator finishes, but they do not appear in the next compaction block if the next compaction snaps before they are dropped.
</Note>

<Warning>
Long-term `.memory/` files do not roll back under `/tree`. A `/tree` rewind that returns to a branch position before a consolidation was triggered will restore the short-term observation buffer (via ledger rollback), but the topic files on disk are unchanged. If a subsequent consolidator run for the same observations is triggered on the rewound branch, the consolidator will see the already-updated topic files and deduplicates naturally on its next rewrite, since it writes current-state prose rather than appending changelogs.
</Warning>
